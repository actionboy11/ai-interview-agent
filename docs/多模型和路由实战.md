# 多模型和路由实战 —— LlmProviderRegistry 设计与实现

> 代码位置：`app/src/main/java/interview/guide/common/ai/LlmProviderRegistry.java`（464 行）
> 关联文件：`ApiKeyEncryptionService`、`ApiPathResolver`、`LlmEmbeddingConfig`、`LlmProviderProperties`、`LlmProviderBootstrapService`、`LlmProviderConfigService`、`LlmProviderController`

---

## 一、这个组件是什么

**LlmProviderRegistry 是整个系统的「多模型接入层」，也是所有 LLM 调用的路由中心。**

系统里所有需要调用大模型的地方——出题、简历评分、JD 解析、面试评估、知识库问答、语音对话——都不直接创建模型客户端，而是向这个注册表要一个 `ChatClient`：

```java
// 业务代码里随处可见的形态
ChatClient chatClient = llmProviderRegistry.getPlainChatClient(provider);
chatClient.prompt().system(...).user(...).call().content();
```

它承担四件事：

| 职责 | 说明 |
|---|---|
| **路由** | 决定这次调用用哪家厂商、哪个模型 |
| **构建** | 按统一协议装配 ChatClient / ChatModel / EmbeddingModel |
| **缓存** | 复用已构建的实例，避免重复建连接 |
| **治理** | 密钥解密、启用校验、配置热切换、降级兜底 |

一句话概括它的价值：**让「换模型」变成改一行配置，而不是改一处代码。**

## 二、要解决什么问题（四个真实痛点）

### 痛点 1：各家「OpenAI 兼容」其实不统一

配置里同时存在两种 baseUrl 写法：

```yaml
dashscope: { base-url: https://dashscope.aliyuncs.com/compatible-mode/v1 }  # 含 /v1
deepseek:  { base-url: https://api.deepseek.com }                           # 不含
glm:       { base-url: https://open.bigmodel.cn/api/coding/paas/v4 }        # 含 /v4
```

而 OpenAI SDK 的请求路径是写死的 `{baseUrl}/chat/completions`。不做归一化，DeepSeek 会 404、Kimi 会拼成 `/v1/v1`。

### 痛点 2：不同业务场景需要不同的「调用用法」

同样是调模型，各场景的要求互相冲突：

| 场景 | 要求 | 冲突点 |
|---|---|---|
| 出题 / 评分 / JD 解析 | 必须返回**可解析的 JSON** | 一旦模型返回 `tool_call` 消息，JSON 解析就失败 |
| 语音面试 | 需要**流式 + 工具调用** | 但对话历史是手工管理的，不能被 Memory Advisor 再插一手 |
| 通用对话 | 需要**完整能力**（工具 + 记忆） | — |

如果在业务代码里用 if-else 兼容，会污染每个调用点。

### 痛点 3：配置要能运行时改，且不能重启

用户在设置页切换默认模型、改 API Key，期望立即生效。

### 痛点 4：API Key 不能明文落库

密钥既要持久化（多实例共享），又不能明文存储。

## 三、核心设计：两级路由 + 三级缓存

这是整个组件最核心的设计，也是简历里最值得写的一点。

```
第一级路由：providerId  →  OpenAiChatModel        （选「厂商与模型连接」）
第二级路由：配方后缀    →  ChatClient              （选「调用用法」）

三级缓存（CacheHolder 内三个 Map）：
  clients          : "dashscope" / "dashscope:plain" / "dashscope:voice"  →  ChatClient
  chatModels       : "dashscope"                                          →  OpenAiChatModel
  embeddingModels  : "dashscope"                                          →  EmbeddingModel
```

### 为什么必须拆成两级

| 维度 | 第一级（ChatModel） | 第二级（ChatClient） |
|---|---|---|
| 决定什么 | baseUrl、apiKey、model 名、temperature | 挂不挂工具、带哪些 Advisor |
| 变化频率 | 用户改配置才变 | 代码写死，每种业务固定一套 |
| 构建成本 | **高**（OpenAI SDK client + HttpClient 连接池） | 低（只是包装） |
| 一个 provider 有几份 | **1 份** | 最多 3 份（`默认` / `:plain` / `:voice`） |
| 缓存 key | `providerId` | `providerId + ":配方"` |

**关键收益**：三种配方**共享同一个模型连接实例**。如果不拆两级，`getChatClient` / `getPlainChatClient` / `getVoiceChatClient` 会各自创建一个 `OpenAiChatModel`，也就是**同一个厂商建三套 HTTP 连接池**。

代码落点在 `getChatModel`（`:233`）——三个 `createXxxChatClient` 都汇流到它：

```java
private OpenAiChatModel getChatModel(String providerId) {
    return cache.chatModels.computeIfAbsent(providerId, id -> buildChatModel(id));
}
```

### 三级缓存的容器（`:458`）

```java
private static final class CacheHolder {
    private final Map<String, ChatClient> clients = new ConcurrentHashMap<>();
    private final Map<String, OpenAiChatModel> chatModels = new ConcurrentHashMap<>();
    private final Map<String, EmbeddingModel> embeddingModels = new ConcurrentHashMap<>();
}
```

由外层用单个 `volatile` 引用持有（`:53`）：

```java
private volatile CacheHolder cache = new CacheHolder();
```

用容器而非三个独立字段，是为了让 `reload()` 能**一次性原子替换**（见 4.5）。

## 四、完整流转

### 4.1 配置从哪来（三层来源）

```
┌── 第 1 层：冷启动播种（只在数据库为空时执行一次）
│     application.yml 的 app.ai.providers.*（api-key 全是 ${XXX_API_KEY} 环境变量占位）
│       ↓ LlmProviderBootstrapService.seedProvidersIfNecessary()  @PostConstruct @Transactional
│       ↓ ApiKeyEncryptionService.encrypt() 加密
│     PostgreSQL: llm_provider_config（密文）+ llm_global_setting（默认 provider 单例行）
│
├── 第 2 层：运行时读配置（DB 模式，默认）
│     LlmProviderRegistry.loadProviderOrThrow()  ← 全类唯一的配置出口
│
└── 第 3 层：legacy 文件模式（repository 为 null 时，如单元测试）
      ~/.interview-guide/llm-providers.yml + llm-providers.env
        ↓ loadProviderFromPropertiesOrThrow()
```

三个来源最终都产出**同一个不可变快照 `ProviderSnapshot`**，上层完全感知不到数据来自哪里。

### 4.2 一次调用的完整时序

以「生成面试题目」调用 `getPlainChatClient(null)` 为例：

```
1. getPlainChatClient(null)                              :139
2.   resolveProviderId(null)                             :347
3.     resolveDefaultChatProviderId()                    :353
4.       globalSettingRepository.findById(SINGLETON_ID)  → "dashscope"
5.   cache.clients.computeIfAbsent("dashscope:plain")    :141  ← 未命中
6.     createPlainChatClient("dashscope")                :198
7.       getChatModel("dashscope")                       :233
8.         cache.chatModels.computeIfAbsent("dashscope") :234  ← 未命中
9.           buildChatModel("dashscope")                 :240
10.            loadProviderOrThrow("dashscope")          :378  ← 唯一配置出口
11.              providerRepository.findById()           :382
12.                .filter(isEnabled)                    :383  ← 禁用 == 不存在
13.              encryptionService.decrypt(nonce, ciphertext)  :388  ← 解密
14.            ApiPathResolver.buildOpenAiClient(baseUrl, apiKey)  :245  ← baseUrl 归一化
15.            OpenAiChatModel.builder()...build()        :252
16.      buildSafeGuardAdvisor()                          :334  ← plain 配方只加这一个
17.      ChatClient.builder(model).defaultAdvisors(...).build()   :201
18. 返回 ChatClient
```

**第二次调用**：第 5 步直接命中 `"dashscope:plain"`，**6~17 步全部跳过**——不查库、不解密、不建连接。

### 4.3 默认 provider 的解析规则

`resolveDefaultChatProviderId`（`:353`）三级兜底：

```
① llm_global_setting 表（SINGLETON_ID = 1）的 default_chat_provider_id
      ↑ 设置页 PUT /api/llm-provider/default-provider 写这里
② application.yml 的 app.ai.default-provider（默认 "dashscope"）
③ repository 为 null（legacy 模式）→ 直接用 properties
```

向量侧对称（`:363`），多一层 `default-embedding-provider` 兜底。

### 4.4 三种配方的分流

| 配方 | 入口方法 | 缓存 key | 工具 | Advisor 链 | 典型调用方 |
|---|---|---|---|---|---|
| 默认 | `getChatClient` `:112` | `"dashscope"` | ✅ | ToolCall + Memory(可配) + Logger(可配) + SafeGuard | 通用对话 |
| **plain** | `getPlainChatClient` `:139` | `"dashscope:plain"` | ❌ | **仅 SafeGuard** | 出题、评分、JD 解析 |
| **voice** | `getVoiceChatClient` `:148` | `"dashscope:voice"` | ✅ | ToolCall(强制保留工具历史) + SafeGuard，**无 Memory** | 语音面试每轮 |

三者的构建方法（`:182` / `:198` / `:206`）差异一目了然，比在一个方法里堆 if-else 清晰得多。

### 4.5 缓存失效流程

```java
public void reload() {                                    // :161
    CacheHolder previous = cache;
    int size = previous.clients.size() + previous.chatModels.size() + previous.embeddingModels.size();
    cache = new CacheHolder();                            // ← 一次赋值，三个 Map 原子切换
    log.info("... Cache invalidated ({} entries dropped). Next access will rebuild clients.", size);
}
```

**为什么是「替换容器」而不是「逐个 clear」**：

| 方案 | 并发问题 |
|---|---|
| `clear()` 三个 Map | 在途线程可能已读到旧配置、正在构建，`clear()` 之后它把**旧配置构建的实例 put 回同一个 Map** → 缓存里长期是陈旧客户端 |
| **替换 CacheHolder**（现方案） | 在途线程持有的是**旧容器引用**，结果写进被丢弃的旧容器；新请求从新容器开始，**不存在回填窗口** |

**为什么必须三个一起换**：若只换 `clients` 而保留 `chatModels`，新建的 ChatClient 会复用旧配置构建的模型连接（旧 model 名 / 旧 baseUrl / 旧 apiKey），导致改配置不生效。用单一引用持有容器，天然保证三者同步。

**语义澄清**：`reload()` 的真实语义是「**缓存整体失效 + 下次访问懒重建**」，它不查库、不重建客户端。所以写操作（新增/修改 provider、切换默认模型）在事务内改完 DB 后调它一遍，配置即刻生效。

## 五、方法地图（命名规约）

这个类方法较多，但命名前缀严格分层，理解了前缀就不用"跳来跳去"：

| 前缀 | 含义 | 方法 |
|---|---|---|
| `get` | **对外入口**，走缓存 | `getChatClient` `getDefaultChatClient` `getChatClientOrDefault` `getPlainChatClient` `getVoiceChatClient` `getEmbeddingModel` `getDefaultEmbeddingModel` |
| `create` | 缓存未命中时**构建大件** | `createChatClient` `createPlainChatClient` `createVoiceChatClient` `createEmbeddingModel` |
| `build` | 构建**零件** | `buildChatModel` `buildDefaultAdvisors` `buildToolCallAdvisor` `buildSafeGuardAdvisor` |
| `resolve` | **算出一个值** | `resolveProviderId` `resolveDefaultChatProviderId` `resolveDefaultEmbeddingProviderId` `resolveEmbeddingDimensions` |
| `load` | 从**配置源**加载 | `loadProviderOrThrow` `loadProviderFromPropertiesOrThrow` |

调用方向永远单向：`get → create → build → load`，不会反向。

### 4 个易混方法的精确区别

```java
getChatClient(id)          // id 由调用方指定，无效则抛异常
getDefaultChatClient()     // = getChatClient(resolveDefaultChatProviderId())
getChatClientOrDefault(id) // = getChatClient(resolveProviderId(id))  ← id 空则回落默认
```

| 传入 `getChatClientOrDefault` | 结果 |
|---|---|
| `null` / `""` / `"   "` | ✅ 回落全局默认 |
| `"dashscope"`（存在且 enabled） | ✅ 正常返回 |
| `"feishu"`（不存在） | ❌ 抛 `IllegalArgumentException` |
| 存在但 `enabled = false` | ❌ 同上（`filter(isEnabled)` 拦截） |

另：`resolveProviderId`（算字符串）vs `resolveDefaultChatProviderId`（查库取默认）——名字像，但一个返回「入参或默认」，一个返回「默认本身」。

## 六、核心设计亮点（简历可用的技术点）

### 亮点 1：两级缓存分离「连接」与「用法」⭐

**问题**：一个厂商的模型连接（含 HTTP 连接池）构建成本高，但业务需要多种 Advisor 组合。

**做法**：ChatModel 按 `providerId` 缓存，ChatClient 按 `providerId:配方` 缓存。三种配方共享同一个模型连接。

**收益**：同一厂商只建一套连接池，同时保留配方灵活性。

**可量化表述**：3 种调用配方共享 1 个模型连接实例，连接数从 3N 降为 N。

### 亮点 2：用「配方隔离」解决结构化输出与工具调用的冲突 ⭐

**问题**：结构化输出（`BeanOutputConverter` 解析 JSON）与 Tool Calling 天然冲突——挂了工具，模型可能返回 `tool_call` 消息而非 JSON，解析直接失败。

**做法**：不在业务代码里做兼容，而是在 **client 级别隔离**——`getPlainChatClient` 返回的 client **既不带 `defaultTools`，也不挂 `ToolCallingAdvisor`**，只保留 SafeGuard。

代码注释原话（`:136-137`）：
> "获取不带 SkillsTool 的 ChatClient，用于结构化输出场景（出题、简历评分等）。这些场景要求模型一次性返回可解析 JSON，不应混入工具调用消息。"

**收益**：业务代码零感知；`getPlainChatClient` 一个方法名就表达了契约。

### 亮点 3：委托型 EmbeddingModel Bean —— 动态换向量模型对 VectorStore 零侵入 ⭐

`LlmEmbeddingConfig`（32 行）注册的 Bean 是一个**纯委托壳**：

```java
@Bean
public EmbeddingModel embeddingModel(LlmProviderRegistry registry) {
    return new EmbeddingModel() {
        @Override public EmbeddingResponse call(EmbeddingRequest request) {
            return registry.getDefaultEmbeddingModel().call(request);   // 每次调用转发
        }
        @Override public float[] embed(Document document) {
            return registry.getDefaultEmbeddingModel().embed(document);
        }
    };
}
```

pgvector 的 `VectorStore` 自动配置依赖这个 Bean。于是：

> **用户在设置页把默认向量模型从 DashScope 换成 GLM，知识库的向量化 / 检索链路一行代码都不用改，因为「会变的那个东西」被藏在接口实现内部了。**

这是「面向接口解耦」的教科书用法。

### 亮点 4：配置双源 + 不可变快照，屏蔽来源差异

`loadProviderOrThrow`（`:378`）是**全类唯一的配置出口**：

```java
if (providerRepository == null) {
    return loadProviderFromPropertiesOrThrow(providerId);   // 文件模式
}
LlmProviderEntity entity = providerRepository.findById(providerId)
    .filter(LlmProviderEntity::isEnabled)                   // 禁用 == 不存在
    .orElseThrow(() -> new IllegalArgumentException("Unknown LLM provider: " + providerId));
return new ProviderSnapshot(
    entity.getId(), entity.getBaseUrl(),
    encryptionService.decrypt(entity.getApiKeyNonce(), entity.getApiKeyCiphertext()),  // 解密
    entity.getModel(), ...);
```

三个设计决策值得说明：

**① 为什么返回 `ProviderSnapshot` 而不是 JPA Entity**

| 原因 | 说明 |
|---|---|
| 不泄漏 Entity | Entity 是托管对象，脱离 Session 访问字段会抛 `LazyInitializationException`；快照是普通 record，可安全作为缓存值被多线程共享 |
| 不可变 = 线程安全 | record 天然不可变 |
| 与表结构解耦 | 快照里是**解密后的 `apiKey` 一个字段**，表里是 `nonce` + `ciphertext` 两列——表结构变化不影响上层 |
| 最小字段集 | 只含构建模型所需字段，不含 `builtin` / `createdAt` / `updatedAt` |

**② 为什么不缓存**
缓存刻意放在上层（`chatModels` / `embeddingModels`），本方法只在缓存未命中时执行。**如果它自己缓存，配置改动就不会生效了**——这正是 `reload()` 能起作用的前提。

**③ `OrThrow` 命名约定**
表示「失败抛异常，绝不返回 null」，调用方无需空判断。

### 亮点 5：全配置驱动的 Advisor / 工具装配

`buildDefaultAdvisors`（`:292`）只做编排，所有组件受配置开关控制：

| Advisor | 作用 | 开关 | 默认 |
|---|---|---|---|
| `ToolCallingAdvisor` | 驱动「模型要求调工具 → 执行 → 结果回灌 → 再问模型」循环 | `app.ai.advisors.tool-call-enabled` | ✅ |
| `MessageChatMemoryAdvisor` | 自动对话记忆（`Math.max(20, maxMessages)` 有下限保护） | `message-chat-memory-enabled` | ❌ |
| `SimpleLoggerAdvisor` | 请求/响应日志 | `simple-logger-enabled` | ❌ |
| `SafeGuardAdvisor` | 敏感词熔断（返回 `Optional`） | `safeguard-enabled` | ✅ |

**降级设计**：`ToolCallingManager` 是 `@Autowired(required = false)`，为 null 时只 `log.warn` 跳过而不报错——保证「没有工具能力也能启动」。

**`SafeGuardAdvisor` 用 `Optional` 返回**（`:334`）：它是唯一可能不存在的组件，用 `Optional.empty()` 让这件事在类型上可见，调用方 `ifPresent(advisors::add)` 一行处理。

### 亮点 6：密钥全生命周期治理

| 环节 | 实现 |
|---|---|
| 算法 | `AES/GCM/NoPadding`，12 字节随机 nonce，128-bit tag |
| 存储 | 拆两列 `api_key_nonce` + `api_key_ciphertext`（都 Base64） |
| 密钥来源 | 环境变量 `APP_AI_CONFIG_ENCRYPTION_KEY` |
| 密钥派生 | 先尝试 Base64 解码，**恰好 32 字节直接作 AES-256 key**，否则 SHA-256 派生 |
| 强制策略 | `require-encryption-key` 默认 `true` → **不配就启动失败** |
| 开发兜底 | 只有同时打开 `allow-fallback-encryption-key` 才用硬编码 dev key |
| 展示脱敏 | `maskApiKey` → `前3 + *** + 后3`（长度 ≤6 全打码） |

**GCM 而非 CBC**：GCM 是认证加密，密文被篡改会在解密时抛异常，而不是静默产出错误明文。

### 亮点 7：并发安全的缓存失效（CacheHolder + volatile）

见 4.5。核心是**用「引用替换」代替「集合清空」**，让失效操作天然免疫「在途构建回填」问题，同时保证三个缓存原子切换。

### 亮点 8：统一 OpenAI 兼容协议 + `ApiPathResolver` 归一化

所有厂商都用 `OpenAiChatModel` / `OpenAiEmbeddingModel`（唯一模型依赖是 `spring-ai-starter-model-openai`，且 `App.java` 显式排除了 6 个 OpenAI 自动配置类——**ChatModel 完全自建，不走自动装配**）。

厂商差异被压缩成「baseUrl 不同」+ 「baseUrl 里的版本段写法不同」，后者由 68 行的 `ApiPathResolver` 吸收：

```java
private static final Pattern TRAILING_VERSION = Pattern.compile("/v\\d+[a-zA-Z0-9]*$");

public static String resolveVersionedBaseUrl(String baseUrl) {
    String stripped = stripTrailingSlashes(baseUrl);
    if (baseUrlContainsVersion(stripped)) return stripped;
    return stripped + "/v1";     // 补默认版本段
}
```

三个细节：

1. `stripTrailingSlashes` **必须在判断之前**执行——否则 `https://api.moonshot.cn/v1/` 因末尾斜杠匹配不上正则，会被补成 `/v1/v1`。
2. 正则是 `v\d+` 而非 `v1`——**GLM 是 `/v4`、豆包是 `/v3`**，写死 v1 会把它们误判。
3. 版本段必须在**末尾**才算数（`https://api.example.com/v1/proxy` 不支持），这是一条明确的能力边界。

**收益**：填 `https://api.deepseek.com` 和填 `https://api.deepseek.com/v1` 等价，用户不需要记住规约。**新增一个 OpenAI 兼容厂商 = 加一条配置，零代码改动。**

### 亮点 9：防御式工程细节

| 细节 | 位置 | 价值 |
|---|---|---|
| 可选依赖 `@Autowired(required=false)` | `:82-86` | 缺少工具/埋点能力时降级而非启动失败 |
| 单测专用 4 参构造器 | `:96-102` | 不依赖 DB 即可测试 |
| `looksLikeChatModel` 前缀黑名单 | `:429` | **在构建前**拦截「把聊天模型填进 embedding 配置」，并给出推荐模型名 |
| `supportsEmbedding` 推导 | `:404` | 文件模式只配 `embedding-model` 也能工作 |
| `resolveEmbeddingDimensions` 兜底 | `:422` | 维度未配时回落全局默认 1024 |
| 嵌套 `computeIfAbsent` 契约注释 | `:225-232` | 明确「两个缓存不可合并」的隐含前提 |

## 七、可靠性、降级与失败语义

### 降级路径总览

| 场景 | 行为 |
|---|---|
| providerId 为 `null` / 空白 | 回落全局默认 provider |
| provider 不存在或 `enabled=false` | 抛 `IllegalArgumentException`（**无兜底**） |
| 工具能力缺失（`ToolCallingManager` 为 null） | warn 跳过 ToolCallingAdvisor |
| 埋点缺失（`ObservationRegistry` 为 null） | 降级为 `ObservationRegistry.NOOP` |
| 加密密钥未配置 | **启动失败**（`require-encryption-key` 默认 true） |
| embedding 模型未配置 | 抛 `BusinessException`，带明确提示 |
| embedding 模型配成了聊天模型 | **构建前**拦截，附推荐模型名 |

### 调用方对异常的处理差异（值得注意）

| 调用方 | provider 无效时的表现 |
|---|---|
| `InterviewSessionService:491`（生成报告） | 抛到全局异常处理器 → HTTP 200 包 `BAD_REQUEST` |
| `InterviewEvaluationRabbitConsumer:118` | 抛在消费逻辑内 → 走重试 → 最终死信 |
| `DashscopeLlmService:55-58`（语音） | `catch (Exception)` → 转成「AI 服务暂时不可用」文案继续对话（**会掩盖配置错误**） |

这说明「统一降级语义」是后续可以改进的方向。

## 八、相关概念补充

### Advisor 是什么

**Advisor 是 Spring AI 的「拦截器链」——拦截的不是 HTTP 请求，而是「对 LLM 的一次调用」。**

| 熟悉的概念 | 拦截对象 |
|---|---|
| Servlet `Filter` | HTTP 请求 |
| Spring MVC `HandlerInterceptor` | Controller 方法 |
| AOP `@Around` | 方法调用 |
| **Spring AI `Advisor`** | **一次 LLM 调用** |

执行是**洋葱模型**：请求从外往内穿过每个 Advisor 到达模型，响应再从内往外穿回。请求方向可改写 prompt，响应方向可改写/短路响应。

**为什么需要**：LLM 调用有一堆与业务无关的横切关注点（工具循环、对话记忆、日志、安全拦截）。挂到 Advisor 链上后，业务代码永远只写 `chatClient.prompt().user(...).call()`。

### ChatModel vs ChatClient

| | ChatModel | ChatClient |
|---|---|---|
| 是什么 | **模型连接**（协议实现 + HTTP 客户端 + 连接池 + 默认 options） | **调用门面**（prompt 构建 + Advisor 链 + 工具集） |
| 本项目中 | `OpenAiChatModel` / `OpenAiEmbeddingModel` | `ChatClient` |
| 构建成本 | 高 | 低 |
| 缓存粒度 | 按 providerId（1 份） | 按 providerId + 配方（最多 3 份） |

### Tool Calling 的两个必备组成

| 组成 | 位置 | 作用 |
|---|---|---|
| `defaultTools(...)` | `:187` / `:211` | **声明**「你有这些工具可用」 |
| `ToolCallingAdvisor` | `:327` | **执行引擎**：真正调工具并把结果回灌给模型 |

只声明不挂 Advisor，模型只会说「我要调用 X 工具」然后结束——**没人执行它**。

### `ConcurrentHashMap.computeIfAbsent` 的使用约束

`computeIfAbsent` 的映射函数中**禁止修改同一个 Map**（会抛 `IllegalStateException` 或并发下死循环）。本项目的 `clients` 与 `chatModels` 是两个独立 Map，所以嵌套调用是安全的——这个前提已写入代码注释（`:225-232`）。

### OpenAI 兼容协议

多数国内厂商（DashScope、Kimi、DeepSeek、GLM、SiliconFlow、本地 LM Studio）都提供 OpenAI 格式的 `/chat/completions` 与 `/embeddings` 端点。因此可以**用同一套 SDK 接入所有厂商**，差异只剩 `baseUrl` 与模型名。这是「新增厂商零代码」的技术基础。

## 九、简历怎么写

### 推荐条目（可直接使用）

> **多模型接入层设计与实现（个人项目 · 核心模块）**
> 设计并实现 LLM 接入与路由层 `LlmProviderRegistry`，支撑 5 家 OpenAI 兼容厂商（DashScope / DeepSeek / Kimi / GLM / LM Studio）的接入与运行时切换：
> - 采用 **providerId → ChatModel → ChatClient（配方）** 两级缓存架构，使 3 种调用配方共享同一模型连接，连接实例数由 3N 降为 N；上层业务与模型供应商完全解耦。
> - 通过 **client 级配方隔离**解决「结构化输出」与「Tool Calling」的冲突：为 JSON 场景提供不挂工具与工具调度 Advisor 的独立 client，保证出题、评分等场景的 JSON 解析稳定性。
> - 用**委托型 `EmbeddingModel` Bean** 实现向量模型的运行时切换，对 pgvector `VectorStore` 零侵入。
> - **配置双源（DB / 文件）+ 不可变快照**统一配置读取出口，支持不重启切换默认模型；**AES-GCM 加密落库 + 强制密钥配置**实现 API Key 全生命周期治理。
> - 缓存失效采用 **volatile 容器整体替换**，消除并发刷新下「旧配置回填」的竞态，并保证三级缓存原子切换。

### 篇幅更短的版本（一条式）

> 设计实现多 LLM 接入层：两级缓存（模型连接 / 调用配方）使三种配方共享连接，client 级隔离解决结构化输出与 Tool Calling 冲突；配置双源 + 不可变快照支持运行时热切换，API Key 以 AES-GCM 加密存储；委托型 EmbeddingModel Bean 实现向量模型动态切换且对 VectorStore 零侵入。

### 面试讲解顺序（建议 90 秒）

1. **先讲问题**：「各家 OpenAI 兼容其实不统一，而且不同业务对模型的用法要求互相冲突。」
2. **再讲结构**：「所以做了两级路由——一级按 providerId 选模型连接，二级按业务配方选用法。连接按 provider 缓存一份，三种配方共享。」
3. **给具体收益**：「结构化输出那条链路刻意不带工具，因为在 client 级别隔离比在业务代码里兼容干净得多。」
4. **补一个亮点**：「向量模型那边用了一个纯委托的 EmbeddingModel Bean，所以设置页换向量模型时，VectorStore 那边一行代码都不用改。」
5. **主动说一个自己修的问题**：「缓存失效我原来用 clear，后来发现并发下会把旧配置的实例回填回去，改成用 volatile 容器整体替换了。」

### 高频追问与答法

| 问题 | 答题要点 |
|---|---|
| 切模型要重启吗？ | 不用。改 `llm_global_setting` 后 `reload()` 让缓存整体失效，下次访问懒重建；且默认 provider 是**每次取用时才解析**的，即使不清缓存也能切到新的。 |
| 为什么 ChatModel 和 ChatClient 分两级缓存？ | Advisor/工具是 client 级、模型连接是 provider 级。共享模型连接省连接池，分离 client 保留配方灵活性。 |
| 在途请求会受切换影响吗？ | 不会。`ChatClient` / `OpenAiChatModel` 不可变且无状态，在途调用持有旧引用跑完，新请求走新实例。 |
| 怎么防止把聊天模型填进 embedding？ | 构建前用前缀黑名单（`glm-`、`deepseek`、`qwen` 等）检测，命中即抛异常并给出推荐模型名。 |
| 缓存并发安全吗？ | Map 本身是 `ConcurrentHashMap`；刷新用 volatile 容器整体替换，在途构建写入被丢弃的旧容器，不存在回填窗口。**主动补充**：跨容器的中间态（新 clients + 旧 chatModels）因整体替换已消除。 |
| 支持非 OpenAI 协议吗？ | **如实说**：当前只覆盖 OpenAI 兼容协议，接 Anthropic / Gemini 原生协议需要新增 Model 实现。 |

## 十、已知不足与改进方向

面试时被问到「还有什么问题」时，主动说这些比被问倒更好：

| # | 问题 | 位置 | 改进方向 |
|---|---|---|---|
| 1 | `reload()` 每次清空全部缓存，改一个 provider 会导致所有连接重建（无定向失效） | `:161` | 按 key 定向失效，或引入 TTL |
| 2 | `resolveDefaultChatProviderId` 每次调用都查库，无缓存 | `:353` | 加短 TTL 的本地缓存 |
| 3 | 模型参数只治理了 `model` + `temperature`，`maxTokens` / `topP` 未支持 | `:247` | 扩展 `ProviderConfig` 字段 |
| 4 | 超时硬编码在 `ApiPathResolver`（connect 10s / read 300s），不可按 provider 配置 | `ApiPathResolver:15-16` | 提为配置项 |
| 5 | 无 API Key 轮换机制（无 keyId / 无 AAD），换加密密钥会导致历史密文不可解 | `ApiKeyEncryptionService` | 引入密钥版本号 |
| 6 | 无效 providerId（非空但不存在/被禁用）无兜底，异步链路会一路走到死信 | `:378` | 统一为「回落默认 + 告警」 |
| 7 | 默认 provider 的写入不校验 `enabled`，可被设成禁用项 | `LlmProviderConfigService:455` | 写入口增加校验 |
| 8 | Advisor 装配全局统一，无法按 provider / 场景定制 | `:292` | 支持 provider 级 Advisor 覆盖 |
