# 文字面试有边界动态追问设计（第二批）

日期：2026-10-29。状态：独立 builder check 已通过，用户已批准设计，进入实施计划复核；尚未开始业务代码修改或数据库迁移。

## 1. 目标与已确认边界

第一批已实现覆盖优先的 V2 主问题规划及主问题/追问计数。本批使追问根据当场回答生成，不推翻该规划器。

用户已确认：

- 整场主问题题槽、类别覆盖和主问题顺序在开始前确定，不在作答中重新规划。
- 当前主问题的回答及此前追问共同决定是否继续追问；回答充分则进入下一主问题，不凑次数。
- 每道主问题最多追问 2 次；整场最多追问 N 次，N 为主问题数量。预算是上限，不是目标。
- 明确表示不会时结束当前主问题组，不强制降低难度继续追问；主动跳过也结束该组，但二者分开记录。
- 追问调用超时、失败或结果不可用：保留答案、提示追问暂不可用、进入下一主问题，不套用固定追问，不因系统故障扣分。
- 临时追问判断不直接修改长期画像。正式评价完成后，按已有证据提取、建议和确认流程更新记忆。
- 本批只承诺文字面试的动态追问闭环，不承诺严格语义去重、跨场知识点覆盖优化、语音动态追问、自由 Agent 或中途重排主问题。

## 2. 方案与取舍

讨论过的方案：提前生成固定追问（现状，不能基于真实回答）、固定主问题加有预算动态追问、模型中途自主调整整场面试。
用户选择第二种。它新增每次有效作答后的模型决策等待，但保留整场知识面和确定的成本上界；第三种会改变已确认的覆盖与顺序，不采用。

以下具体技术选择原作为实现建议提交，已随整份设计获用户批准；具体实施任务仍需复核。
沿用 Java/Spring Boot、PostgreSQL、Redis Stream、React，不增加工作流引擎、向量库或第二套身份系统。

## 3. 代码现状与改造边界

- `InterviewSessionService.createSession` 收集画像/历史后调用规划器；`InterviewQuestionService.generateFromPlan` 当前一次生成主问题及固定追问。
- `submitAnswer` 当前按 `questionIndex + 1` 推进，末题即完成并发布评价任务；不能原样用于等待动态决策。
- `questionsJson`、答案唯一键 `(session_id, question_index)`、缓存恢复及前端均依赖稳定的原始索引。
- `AnswerEvaluationService` 当前将问题转换为 `QaRecord`，未携带跳过、故障、主追问组关系等动态上下文；不能仅修改提示词就假定这些信息已打通。
- 正式报告保存后由 `MemoryDerivationPublicationService` 发布记忆推导；本批延续该确认边界，扩充输入语义，不在追问消费者中写画像。
- `InterviewQuestionService` 存在用户未提交改动；实施时必须先检查差异，小范围调整，不能覆盖或混入提交。

## 4. 主问题、实际问答与决策分离

### 4.1 会话版本与计划

新增持久化会话执行模式 `LEGACY_FIXED` / `DYNAMIC_FOLLOW_UP`，缺失按旧模式读取。它独立于规划算法版本：V2 仍表示覆盖优先，不能通过计划 V2 推断为动态面试。
建议新建文字面试默认动态，旧会话不迁移执行模式、不补题或重写计划，旧客户端缺少动态能力时不允许误入动态创建入口。

主问题生成仍一次完成，使用动态专用结构化输出：每题包含 `slotId`、题面、主题摘要、2–4 条可观察的 `assessmentTargets`。
考查目标与主问题一起生成并保存快照，不额外调用模型，不写入已有 V2 题槽 JSON；无合格目标时走创建阶段有限重试，仍无效则创建失败，不发布半成品。
考查目标用于判断证据是否充分，不是必须逐字背诵的标准答案；默认不向作答页面公开目标清单或参考答案。

### 4.2 数据建议

新增动态运行状态及决策记录，使用正式迁移，不依赖生产 `ddl-auto`：

- `interview_dynamic_runtime`：会话/归属引用、执行版本、运行阶段、不可变主问题与目标快照、当前 `slotId`、当前实际问题索引、已消耗预算、政策快照、乐观锁版本。
- `interview_follow_up_decisions`：会话、归属、源答案/实际问题索引、主问题 `slotId`、决策 ID、状态、投递状态、deadline、租约/尝试令牌、上下文快照、模型动作及原因摘要、最终动作、结束原因、错误码、应用后的运行版本。
- 答案新增动态提交意图（`ANSWER` / `DONT_KNOW` / `SKIP`）及提交请求标识；旧答案缺失意图保持旧语义。草稿与正式提交分开，已提交动态答案本批不允许回改。
- 每个实际问题保存既有 `slotId`、`isFollowUp`、`parentQuestionIndex`；所有追问父题都指向所属主问题，而不是前一道追问。
- 数据库约束保证一次源答案最多一个决策、请求 ID 不复用到另一答案；状态提交以会话锁或条件更新串行化，不能仅靠 Redis 锁维持正确性。

主问题池与实际作答列表必须分开。动态 `questionsJson` 只保存已发布到问答序列的问题：开始只发布第一道主问题；下一步发布追问或下一主问题，并分配末尾新索引。
未来主问题保存在不可变快照中，不预先占用实际索引；因此插入追问不移动任何已有索引。这里的“发布”表示服务端已提供该问题，不证明用户已实际看到页面。
`questionsJson`、运行游标、预算和决策应用在同一短事务内持久化；Redis 是可丢弃缓存，不作为推进真相源。

## 5. 提交与异步状态机

运行阶段：`WAITING_ANSWER`、`DECISION_PENDING`、`COMPLETED`。决策任务另有 `PENDING/PROCESSING/APPLIED/FAILED/CANCELLED`。

1. 鉴权并校验归属、会话模式、运行版本、当前问题及提交请求 ID。
2. 短事务保存正式答案。显式不会/跳过、预算用尽等可由规则直接终结该组；否则创建唯一决策记录，进入 `DECISION_PENDING`，答案与待投递任务同事务提交。
3. 提交响应明确给出运行阶段、版本和决策 ID，不能用 `hasNextQuestion=false` 表示“等待”并误触发交卷。
4. 提交后由投递器将持久化待投递记录发送 Redis Stream；定时补投覆盖 DB 提交后进程崩溃的窗口，允许至少一次投递。使用现有生产/消费模板，不在业务中复制队列重试逻辑。
5. 消费者先检查实体、归属及预期版本；已删除/已完成/已取消任务 ACK 丢弃。短事务认领并固定上下文，事务外调用模型。
6. 短事务校验租约令牌、deadline、决策和运行版本仍有效，再应用一次结果。追问发布时原子增加预算；否则结束该组，发布下一主问题或完成整场。
7. 提交成功后失效缓存。动态读取以 DB 运行版本为准，旧缓存不能覆盖新状态；缓存不可用不回滚已成功的数据库提交。

前端建议用轮询而非新增 SSE：等待期间每 1–2 秒读取会话运行快照，离页取消，恢复页面从 DB 状态继续。轮询只读，不触发模型；响应版本小于页面已应用版本时丢弃。
GET 不负责状态推进，超时由后台恢复任务收敛。等待时允许提前交卷，暂不允许“跳过还没生成的追问”，避免定义额外的并发操作。

## 6. 追问决策协议

输入限于当前主问题的目标、题面、该组已提交问答、目标难度、剩余预算和创建时相关画像摘要；不携带其他用户或全部原始历史。
答案属于不可信数据，不得当作系统指令；模型不能修改类别、主问题计划、预算、用户归属或长期画像。

建议模型响应：

```json
{
  "action": "FOLLOW_UP",
  "reasonCode": "IMPORTANT_GAP",
  "reasonSummary": "尚未确认修复方案的可行性",
  "coveredTargetIds": ["target-1"],
  "missingTargetIds": ["target-2"],
  "followUpQuestion": "你会如何调整调用方式，让事务生效？"
}
```

动作仅 `FOLLOW_UP` / `NEXT_MAIN`；`NEXT_MAIN` 不含追问题面。已充分覆盖返回 `SUFFICIENT`；无有价值可追问内容返回 `NO_USEFUL_FOLLOW_UP`。
允许 `USER_DONT_KNOW` 识别自然语言的明确不会，但不能将“不会发生内存泄漏”等句中否定误判为放弃。页面提供“我不会”和“跳过本题”显式动作，作为确定性退出入口。
普通回答存在歧义时不直接认定不会；可在预算内生成澄清追问。用户显式动作优先，不需要调用模型确认。

后端校验结构、目标 ID、题面长度、动作一致性，拒绝空问题或归一化后与该组题面完全重复的问题；非法输出在统一调用器有限修复后仍无效则故障降级。
相关性、难度与非字面重复不宣称硬保证，以提示约束和固定案例验证。模型理由仅保留简短可解释摘要，不要求或存储思维链。
只有“重要缺口尚待确认、追问能获得有用信息、预算未用完”才继续问；回答充分即停止。追问围绕原目标，不为继续问而引入新目标或不断加深难度。

## 7. 预算、超时、并发与完成

- 单组最多 2 道，整场最多 N 道；只统计已成功持久化发布的追问，重投/模型调用/失败不消耗题数预算。该上限不等于精确模型费用上限。
- 建议总决策 deadline 默认 30 秒，覆盖排队、调用和结构化修复；客户端超时不取消已保存答案。配置集中管理，并在会话创建时保存政策快照。
- 模型重试通过 `StructuredOutputInvoker`；消费者重投前重新检查 deadline 和决策状态，不允许每次重投重置 30 秒。恢复器处理队列不可用、无人认领、租约过期，超过 deadline 即失败并推进。
- deadline 后或提前交卷后的迟到结果不能插题。后端事务先提交者决定终态，另一结果只丢弃/审计。
- 相同请求重试返回原提交结果和最新运行快照，不重新写答案/消耗预算；同源答案不同请求内容拒绝，过期版本或非当前问题拒绝。并发双标签页至多一个推进成功。
- 动态草稿接口不得覆盖已提交答案，也不得在决策期间修改上下文。最后主问题的答案不立即交卷，要先结束其可能的追问链；预算已耗尽或明确不会可立即完成。
- 提前交卷原子冻结实际问题与答案快照、取消未应用决策并触发一次可恢复的正式评价；之后不能再追加问题。
- 自动完成/提前完成均使用持久化待投递记录及幂等评价任务标识，避免“已完成但评价消息丢失”。旧会话流程不顺带重写。
- 会话/简历/账号删除或撤销访问时，在任务认领与应用阶段重新检查有效性；已经在途的外部调用不能保证撤回，但不得落库为新问题。

## 8. 结束原因、正式评价与长期记忆

主问题组结束原因分开保存：`SUFFICIENT`、`NO_USEFUL_FOLLOW_UP`、`DONT_KNOW`、`SKIP`、`BUDGET_EXHAUSTED`、`SYSTEM_UNAVAILABLE`、`EARLY_COMPLETE`。
模型判断仅供导航。正式评价依据原始问答、考查目标、父题关系、提交意图及结束原因，不把临时判断当最终分数。

- `DONT_KNOW`：形成当前具体考查点的不足证据，不能仅据一题把整个 Java 类别认定为薄弱。
- `SKIP`：没有足够能力证据，不能仅据跳过认定不会；该组此前已有的有效回答仍可正常评价。
- `SYSTEM_UNAVAILABLE`：保留并正常评价已提交回答；未生成的追问不创建空答案或 0 分。系统未验证的目标标记未观察，不当错误。
- `BUDGET_EXHAUSTED`：停止不代表充分，按实际证据评价；提前交卷的未作答项标记未观察，不凭空生成不足证据。

动态模式建议采用主问题组聚合，防止“被追问两次就产生三份独立能力证据”：模型对整组作答给主问题组评价与观察到的目标，保留逐作答项反馈。
组评分仅基于可观察回答；完全无有效证据的组分数可空，不显示为 0；明确不会是有效不足证据而不是未知。类别分及总分按有有效评价的主问题组等权汇总，不按追问数量加权；全部无证据时总分未知。
这要求动态专用评价适配、可空评分展示与报告/导出兼容，不能直接把现有所有空答案映射成 0 分的路径用于新模式。旧面试评分不重算。
动态记忆推导输入正式组评价及来源答案引用，同一组作为一个证据单元，保留支持该结论的多个答案引用；无证据组不产出薄弱建议，不绕过现有用户确认流程。
组证据若需兼容现有单答案来源结构，由主问题答案作为稳定锚点，扩展存储本组支持答案引用；接受、编辑、拒绝与归属校验不能丢失这些来源，不另起自动覆盖画像的流程。
当前记忆推导按非空答案及逐题分数筛选并按类别取均值，动态模式必须单独适配：显式不会即使没有文本也保留有效意图证据；按有效组分数计算类别建议，一组只产生一份计数证据，不能继续把所有追问答案独立取均值。旧模式保留现有算法。

## 9. API 与前端兼容

建议动态专用提交/运行状态接口，保留现有固定模式 API；共享创建接口增加客户端声明与持久化执行模式，旧客户端缺省仍创建固定模式，新前端默认声明动态。
动态提交携带 `requestId`、`questionIndex`、`expectedVersion`、`submissionIntent`、答案；显式不会/跳过无需伪造文本，服务端保存真实意图。
运行响应至少含模式、运行阶段/版本、计划主问题数、当前主问题序号、当前实际问题、已发布主/追问计数、已完成主问题组数、已用预算及可公开的状态提示。
面试中明确展示“计划 8 道主问题，当前第 3 道；当前第 1 次追问”。`totalQuestions` 仍指实际已发布作答项数，不宣称最终题数；不得以回答数等于已发布数推断完成。
结束后展示实际主问题/追问/作答项，同时提前交卷时补充原计划数；完整历史、继续面试、首页弹窗、简历关联入口都使用持久化模式分流。
等待状态禁用重复提交；“我不会”“跳过本题”含义区分，追问上的动作同样结束当前主问题组。模型故障提示可见但不展示原始供应商错误或敏感上下文。
新前端恢复旧会话按原固定列表显示；动态模式不兼容旧客户端时返回明确错误，不能把等待伪装成完成。

## 10. 安全、观测与配置

所有入口鉴权、CSRF、归属和 `@RateLimit` 沿用现有机制；队列消息只携带任务引用，消费者从持久化记录取可信归属。
通过 `LlmProviderRegistry.getChatClientOrDefault(provider)` 和 `StructuredOutputInvoker` 调用会话供应商，模板放 `.st`；外部调用不在事务内，事务 Service 独立注入避免自调用失效。
日志仅记录会话/决策标识、动作、耗时、尝试次数及错误码，默认不输出简历和答案正文。追问上下文随会话删除级联清理；失败原因对外脱敏。
新增指标：决策延迟/失败率、追问实际使用数、充分结束/不会/跳过比例、重复任务丢弃数；不为本批建设独立离线评测平台。

## 11. 验收范围

1. 完整回答不追问；重要缺口产生相关追问；合并主问答与追问后充分则停止，避免只看最后一句。
2. 显式/自然语言明确不会结束该组；跳过不误记不会；句中否定不误判。
3. 单组 0/1/2 次、整场上限、最后主问题追问完再结束；追问失败不消耗题数预算。
4. 多标签页、重复提交、草稿迟到、Stream 重投、DB 提交后投递失败、认领后崩溃、迟到结果、提前交卷与删除竞态均不重复推进。
5. Redis 丢失/不可用、页面刷新、服务重启后可从 DB 恢复，不重编号已有问题或答案，不改主问题计划。
6. 动态报告保留实际逐项反馈和组评价；不会、跳过、故障分别处理；未知分数不显示 0，记忆证据来源可追溯且不重复累计追问。
7. 旧 V1/V2 固定面试的题目 JSON、计划、答案索引、报告和评分保持不变；跨用户访问/后台任务安全边界成立。
8. 后端全量测试、前端测试与构建；新增 PostgreSQL 约束/迁移与 Redis 投递恢复的集成验证，H2 不能替代真实锁竞争验收。
9. 使用受控模型替身验收确定性行为；真实模型的题面质量仅在用户授权的少量新测试面试中验收，不能用旧用户数据偷偷重跑评价或制造费用。

## 12. 审核结果与后续步骤
