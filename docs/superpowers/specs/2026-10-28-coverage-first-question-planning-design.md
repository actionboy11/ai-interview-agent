# 综合面试先覆盖再强化与题数口径设计（第一批）

状态：用户已确认设计，进入实施计划阶段，尚未修改业务代码。

## 目标与已确认方向

默认综合面试先覆盖当前方向的分类，再使用剩余主问题进行个性化强化。
本批同时统一主问题、追问与总作答项的展示，不修改历史题目、既有计划或能力记忆。
沿用 Java/Spring Boot、React 与现有规则规划器，不引入工作流引擎或额外模型调用。

## 现状证据

- 三场本地面试分别为 6+6、6+6、8+8（主问题+追问），页面仅显示 12、12、16。
- 创建请求 questionCount 与 QuestionPlan.slots.size 表示主问题数；生成完成后的
  totalQuestions 表示包含追问的作答项数，当前文案未说明区别。
- 第三场 8 道主问题中 PROJECT 与 SYSTEM_DESIGN_SCENARIO 各 3 道，未覆盖 REDIS、SPRING。
- 原分配器提前预留强化容量，基础分配又将静态历史覆盖次数置于本场已分配数之前。

## 方案比较

1. 仅交换基础题排序：改动最少，但预留强化仍可能挤掉核心分类，不足以保证综合覆盖。
2. 覆盖阶段与追加阶段分开（采用）：覆盖是硬约束，个性化使用剩余预算；保留既有画像与模型生成链路。
3. 增加专项/综合模式或模型自主规划：属于新功能与更大改造，本批不采用。

用户已确认默认综合面试采用先覆盖再强化；下述边界与追加预算是本设计提出的实现选择。

## 分类分配

### 第一阶段：覆盖

- 对当前 Skill 的合法分类去重，不在算法中硬编码 Java 的六类。
- 主问题数 N 不少于分类数 C 时，每个分类先安排一道；必考先排列，其余按 CORE、NORMAL、分类 key 稳定排序。
- N 小于 C 时，优先必考，再核心分类，再普通分类；同优先级结合历史覆盖少的优先、分类 key 决胜。
- 必考分类数大于 N 时明确返回参数/规划错误，不悄悄漏掉必考分类。
- 一个题槽只占一个主问题名额，不因为同一分类兼具必考和弱项属性而额外复制一道。
- 首轮保留 MANDATORY/BASELINE 用途，并可携带有效画像摘要指导具体内容；不借本批更改既有难度政策。

### 第二阶段：追加

- R=N-已覆盖主问题数；R 为零则停止，不为了满足旧用途比例破坏覆盖。
- 只对 R 分配基础、弱项、探索、优势预算，建议相对权重延续 4:3:1:1；以最大余数法分配整数。
- 不存在对应候选时，将其预算转为基础覆盖；受分类容量限制未使用的名额也交给基础补齐。
- 弱项、优势沿用有效画像筛选；基础追加排序改为本场分配少优先、历史覆盖少次之、方向优先级和 key 决胜。
- 保留现有分类容量公式 max(ceil(N*0.3), ceil(N/C))，其文案只能称整数容量限制，不能声称严格不超过30%。
- 固定分配、无画像、画像故障回退也遵循第一阶段覆盖，不允许回退路径绕过综合覆盖约束。
- 同一输入结果确定；总题量严格等于 N，不循环查库或调用模型。

以 Java 六类为例：N=6 每类一道；N=8 每类一道加两道个性化题。两道追加给谁由画像与历史决定，
不把“项目2、系统设计2”固化为新固定模板。

### 来源与校验

- 先决定分类，再分配 RESUME/DIRECTION；简历来源必须有事实支撑，简历比例是目标而非覆盖的上级约束。
- 保留现有画像资格、来源安全限制和模型生成服务。
- 新计划使用 version=2；校验总数、唯一slotId、合法分类、必考覆盖、应覆盖分类、分类容量和简历来源。
- 旧 version=1 计划仅用于原面试展示和执行，不按新规则重写或补题。

## 题数与兼容性

- 创建 API 的 questionCount 保持表示主问题数，页面文案改为“主问题数量”。
- 新增只读计数 mainQuestionCount、followUpQuestionCount；totalQuestions 保持总作答项语义，
  currentQuestionIndex、提交答案索引、评分与导出原有题号不重编号。
- 计数来自实际持久化题目列表的 isFollowUp，不依赖固定“主问题乘二”，因为追问可能缺失或配置为0/2。
- 未生成完成的初始记录不作为完整历史面试显示；新计数不能将初始计划数伪装成实际已生成数。
- 无法解析/缺少旧题目列表时，计数返回未知，前端显示已有“总作答项”，不猜测一半是主问题。
- 完整历史题目存在时可动态统计，无需增加数据库计数列或批量改写旧数据。
- 统计逻辑集中复用；历史列表使用已读取的题目数据，不引入逐条额外数据库查询。
- 会话、历史、详情响应与前端共享类型同步；报告/导出原有计分与总项口径保留，不重新生成已保存报告。
- 创建页显示追问生成说明；历史与详情显示“6道主问题 + 6道追问，共12个作答项”。
- 面试作答进度明确使用“作答项”；详情利用已有 isFollowUp/parentQuestionIndex 展示追问归属，保留原始作答索引。
- 旧后端响应不包含新字段时前端降级显示总项，不将 undefined 显示为0。

## 影响范围

- 后端：AdaptiveAllocationPolicy、QuestionPlanValidator、必要的共用覆盖/预算策略；会话、历史、详情计数DTO及映射。
- 前端：创建入口（含复用弹窗）、历史列表、面试进度、详情、共享类型与计数展示工具。
- 不触碰用户已有无关改动；InterviewQuestionService 如必须调整，仅限必要兼容，不整文件覆盖。

## 非目标

本批不做主/追问语义去重、知识点结构化提取、动态追问、优势难度政策调整、专项模式、
模型迁移、记忆评分重算、离线评测系统或历史数据清理。
本批保证分配的覆盖与题数可解释，不声称已经解决题面重复或内容质量问题。

## 验收

1. 用第三场创建时的画像和前两场历史作为固定测试夹具，8题覆盖六类，不再出现3项目+3系统设计并漏Redis/Spring。
2. 6类6题每类一道；无画像和规划故障回退同样成立。
3. N<C、自定义分类、多个必考、必考超预算、单一分类、无弱项/优势、简历事实不足均有明确确定结果。
4. N=6/8/10/12及3至20边界下总量、唯一题槽、覆盖和容量一致；输入集合顺序不影响已定义的稳定排序。
5. 6主+6追问、8主+8追问、零追问、两追问配置和部分缺追问计数正确；旧缺失数据/旧API前端不误报。
6. 已有三场内容、计划JSON、答案、能力画像和评分不变，旧会话继续作答与详情正常。
7. 后端运行完整 :app:test --no-daemon；前端运行 pnpm test 与 pnpm run build。
