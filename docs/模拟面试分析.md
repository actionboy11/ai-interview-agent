# 模拟面试功能分析（文字面试）

> 代码位置：`app/src/main/java/interview/guide/modules/interview/`
> 关联：`common/evaluation/UnifiedEvaluationService`（与语音面试共用评估引擎）、`infrastructure/redis/InterviewSessionCache`、`frontend/src/pages/InterviewPage.tsx`
> 本文包含实现分析 + 2026-09-17 完成的 6 项修复记录。

---

## 一、功能全景

一句话：**配置面试方向 → 一次性生成题单 → 逐题作答 → 交卷触发异步评估 → 产出报告与 PDF**。

| 层 | 位置 |
|---|---|
| HTTP | `InterviewController`（12 个接口） |
| 编排 | `InterviewSessionService`（会话生命周期中心） |
| 出题 | `InterviewQuestionService` + `InterviewSkillService`（技能包） |
| 评估 | `AnswerEvaluationService` → `UnifiedEvaluationService`（与语音共用） |
| 持久化 | `InterviewPersistenceService`（两张表） |
| 缓存 | `InterviewSessionCache`（Redis，24h TTL） |

## 二、数据模型

### 2.1 `interview_sessions`（会话）

| 字段 | 作用 |
|---|---|
| `sessionId` | 16 位 UUID（去横线截断），业务主键，唯一 |
| `questionsJson` | **`TEXT`，整个题单的 JSON 快照**，含题目/分类/答案/分数/反馈 |
| `currentQuestionIndex` | 进度指针 |
| `status` | `SessionStatus`：`CREATED` / `IN_PROGRESS` / `COMPLETED` / `EVALUATED` |
| `evaluateStatus` | `AsyncTaskStatus`：`PENDING` / `PROCESSING` / `COMPLETED` / `FAILED` |
| `evaluationMessageId` | **唯一约束**，评估幂等键 |
| `overallScore` / `overallFeedback` / `strengthsJson` / `improvementsJson` / `referenceAnswersJson` | 报告结果 |

索引：`(resume_id, created_at)`、`(resume_id, status, created_at)`、`(skillId, createdAt)`。

### 2.2 `interview_answers`（逐题作答）

| 字段 | 作用 |
|---|---|
| `session_id` + `question_index` | **联合唯一约束** → 天然 upsert 键 |
| `question` / `category` / `userAnswer` | 题目与回答 |
| `score` / `feedback` / `referenceAnswer` / `keyPointsJson` | 评估后回填 |

⚠️ **注意**：`InterviewAnswerEntity.session` 关联的是 session 的**数值主键 `id`**，不是 `sessionId` 字符串。查询时才通过 `findBySession_SessionIdOrderByQuestionIndex(sessionId)` 做 join。

### 2.3 `questionsJson` 的结构

由 record `InterviewQuestionDTO`（10 字段）序列化：

```json
[
  {
    "questionIndex": 0,
    "question": "请介绍 MySQL 索引下推（ICP）的原理和生效条件",
    "type": "MYSQL", "category": "MySQL",
    "topicSummary": "索引下推原理与生效条件",
    "userAnswer": "ICP 是在存储引擎层过滤…",
    "score": 78, "feedback": "理解基本到位，但未提到…",
    "isFollowUp": false, "parentQuestionIndex": null
  },
  {
    "questionIndex": 1,
    "question": "你刚才提到的覆盖索引，具体怎么判断是否命中？",
    "isFollowUp": true, "parentQuestionIndex": 0
  }
]
```

**一个隐蔽的不一致**：`score` / `feedback` 只在会话期写进 Redis 缓存，而 `restoreSessionFromEntity` 从 DB 恢复时**只回填 `userAnswer`**（`withAnswer`），不还原分数。缓存过期后重建，`questionsJson` 里的分数仍是 null —— 报告里真正的逐题分数来自 `interview_answers` 表。

## 三、状态机：两条**互相独立**的状态轴

理解这个模块的关键，别把它们混成一条线：

```
业务状态 status:          CREATED ──→ IN_PROGRESS ──→ COMPLETED ──→ EVALUATED
                           建会话      首次拉题         交卷完成      报告落库

异步状态 evaluateStatus:  （null）──→ PENDING ──→ PROCESSING ──→ COMPLETED
                                                   └──→ FAILED（重试耗尽 / 超时清理）
```

### 流转的全部触发点

| 流转 | 触发位置 | 条件 |
|---|---|---|
| → `CREATED` | `createSession` | 建会话：先写缓存，再写 DB |
| `CREATED` → `IN_PROGRESS` | `getCurrentQuestion` | **惰性触发**——第一次拉题时顺手改状态 |
| 每次提交 → `IN_PROGRESS` | `persistSubmittedAnswer` | 显式按 `newStatus` 更新 |
| → `COMPLETED` | `submitAnswer` 最后一题 / `completeInterview` 提前交卷 | `newIndex >= questions.size()` |
| `COMPLETED` → `EVALUATED` | `InterviewPersistenceService.saveReport` | 异步消费者评估成功后 |
| → `FAILED` | 消费者重试耗尽 / **超时清理任务** | 进死信，或会话超过 24h 未完成被自动结束 |

### 两个结构性事实

1. **`SessionStatus` 里没有 `FAILED`** —— 评估失败时业务状态仍停在 `COMPLETED`，"失败"只由 `evaluateStatus=FAILED` + `evaluateError` 表达。前端据此区分「已完成 / 评估中 / 评估失败」三种展示。
2. **`SessionStatus` 被定义了两遍**（实体内部类 + `InterviewSessionDTO.SessionStatus`），靠 `convertStatus` 的 switch 手工映射。好处是**新增枚举值时 switch 会编译失败**，不会静默丢状态。

## 四、完整生命周期

```
① 配置           InterviewHubPage：模式/方向/难度/题数/简历；自定义 JD 走 parse-jd
                     ↓ navigate('/interview', { state })
② 建会话         POST /api/interview/sessions
                 InterviewSessionService.createSession
                   ├─ getHistoricalQuestions(skillId, resumeId)    ← 历史题去重
                   ├─ generateQuestionsBySkill(...)                ← 双路并发出题
                   ├─ sessionCache.saveSession(...) status=CREATED ← 先写缓存
                   └─ persistenceService.saveSession(...)          ← 后写 DB（失败回滚缓存并报错）

③ 拉题          GET  /sessions/{id}/question
                     ├─ getOrRestoreSession → 缓存优先，miss 则 DB 恢复 + 回写
                     └─ 惰性置 IN_PROGRESS（缓存 + DB）

④ 逐题作答      POST /sessions/{id}/answers
                 submitAnswer
                   ├─ persistSubmittedAnswer  ← 先写 DB（失败抛 3008）
                   ├─ updateQuestions / updateCurrentIndex         ← 后更新缓存
                   └─ 若最后一题：status=COMPLETED + enqueueEvaluationTask

⑤ 交卷（可选）  POST /sessions/{id}/complete（提前交卷）

⑥ 异步评估      publishEvaluationTask
                   ├─ RabbitMQ（默认）或 Redis Stream（开关切换）
                   ├─ 幂等：evaluateStatus==COMPLETED 或 messageId 相同 → 直接 ACK
                   ├─ 失败：10s/30s/60s 三次重试 → 死信 + evaluateStatus=FAILED
                   └─ 成功：saveReport 写 EVALUATED + 同步缓存状态

⑦ 等评估        记录页 3s 轮询会话列表；详情页在评估中时 3s 轮询详情（本次修复）

⑧ 看报告        GET /sessions/{id}/details（从 DB 读）

⑨ 导出 PDF      GET /sessions/{id}/export → iText + 中文字体内嵌
```

## 五、关键实现细节

### 5.1 出题：双路并发 + 三级降级

`InterviewQuestionService.generateQuestionsBySkill` 用**虚拟线程**（`Executors.newVirtualThreadPerTaskExecutor()`）并发跑两路：

- **简历题**：`resumeCount = round(总题数 × 0.6)`
- **方向题**：剩余 40%，按技能包 categories 三阶段分配名额（`ALWAYS_ONE` 保底 → CORE 优先覆盖 → 剩余轮转）

降级链三级：简历题失败 → 全改方向题；方向题失败 → 只留简历题；都失败 → 兜底题库。

追问在**出题期静态生成**（默认 1 条、硬上限 2 条），作为独立题目占用总题数并单独打分。

历史题去重：取**最近 10 次会话**的主问题（排除追问），`LinkedHashSet` 精确去重后 `limit(60)` 压 token，再把 `topicSummary` 注入 prompt 让 LLM 语义避让。

### 5.2 写 DB 优先、缓存当成可重建的派生态 ⭐

`submitAnswer` 的顺序是**先 DB 后缓存**，且 DB 失败直接抛 `INTERVIEW_ANSWER_SAVE_FAILED(3008)`：

```java
persistSubmittedAnswer(request, index, question, newIndex, newStatus);
// 更新 Redis 缓存。DB 已经持久化成功，缓存失败时可由后续读取从数据库恢复。
sessionCache.updateQuestions(request.sessionId(), questions);
```

这个方向的正确性在于：**Redis 可以随时整体丢失而不丢进度**，因为 `getOrRestoreSession` 能从 DB 完整重建：

```
getOrRestoreSession: 缓存命中 → 刷新 TTL 返回
                     缓存 miss → 查 DB → 解析 questionsJson
                              → 用 interview_answers 回填 userAnswer
                              → 回写缓存 → 返回
```

### 5.3 断点续答

| Redis Key | 值 | TTL |
|---|---|---|
| `interview:session:{sessionId}` | `CachedSession`（questionsJson、currentIndex、status） | 24h |
| `interview:resume:{resumeId}` | `sessionId`（用于找未完成会话） | 24h |

**TTL 刷新只在 `getOrRestoreSession` 里做** —— 只有"继续答题"才延长会话寿命，"打开详情页看一眼"不会。

### 5.4 异步评估：幂等 + 重试 + 死信 + 人工重放

- **幂等双保险**：消费端判 `evaluateStatus == COMPLETED` 短路；落库端 `evaluation_message_id` 唯一列 + `saveReport` 返回 `CREATED / ALREADY_COMPLETED / SESSION_MISSING`。
- **三档延迟重试**：10s / 30s / 60s（TTL + DLX 实现，无插件）。
- **失败可见**：发布失败、消费失败重试耗尽、超时清理——三条路径都会置 `evaluateStatus=FAILED` 并写 `evaluateError`（截断 500 字）。
- **人工兜底**：死信落库，管理端 `POST /api/admin/interview-evaluation/dead-letters/{id}/replay` 可重放。
- **双实现可插拔**：RabbitMQ / Redis Stream 通过 `@ConditionalOnProperty` 切换，消息只带 `sessionId`。

### 5.5 超时清理（本次新增）

`InterviewSessionService.cleanupStaleSessions`，`@Scheduled(fixedRate=1h, initialDelay=10min)`：

```
超过 24h 仍处于 CREATED / IN_PROGRESS 的会话
  → status = COMPLETED
  → evaluateStatus = FAILED，evaluateError = "会话超过 24 小时未完成，已自动结束"
  → 清理 Redis 会话缓存与简历映射
```

设计取舍：**只改状态不删数据**（可逆），会话记录与答案保留；因为不再处于"未完成"状态，不会再被 `findUnfinishedSession` 当成可继续的会话返回。

## 六、设计亮点

1. **缓存是可重建的派生态，不是真相源** —— 写路径 DB 优先、缓存失败只降级；读路径缓存 miss 自动从 DB 重建并回写。Redis 变成纯粹的加速层，可随时清空。
2. **评估链路的完整可靠性闭环** —— 幂等键（唯一约束）+ 三档延迟重试 + 死信审计 + 人工重放，四件套齐全。
3. **历史题去重克制而有效** —— 不引入向量检索，用「最近 10 次会话 + 主问题过滤 + 精确 Set + `topicSummary` 语义避让」就达到可接受的去重效果，且 token 可控。
4. **出题的部分失败不影响全局** —— 双路并发 + 三级降级，任意一路失败都能产出可用题单。
5. **评估引擎与语音面试共用** —— `UnifiedEvaluationService` 通过 `QaRecord` / `EvaluationReport` 两个中性模型承载，两条链路只做 DTO 适配（分批 8 + 二次汇总 + 4 层降级）。

## 七、本次修复的 6 个问题（2026-09-17）

### 🔴 1. 关键写接口参数校验整体失效

**问题**：`createSession` 缺少 `@Valid`，`CreateInterviewRequest` 上的 `@Min(3) @Max(20)`、`@NotBlank skillId` **从不触发**；`questionCount` 是原始类型 `int`，JSON 省略即 `0`，**可以直接建出 0 题会话**。`submitAnswer` / `saveAnswer` 更彻底——用 `Map<String, Object>` 手工取值，`SubmitAnswerRequest` 的校验注解全部形同注释，且 `questionIndex` 传字符串会 `ClassCastException`。

**修复**：`createSession` 加 `@Valid`；两个答案接口改为 `@Valid @RequestBody SubmitAnswerRequest`，`sessionId` 以路径参数为准（因此该字段的 `@NotBlank` 被移除，改为注释说明）。

**验证**：`questionCount=0` 或缺失 `skillId` 的请求现在会被拒绝返回 400。

### 🔴 2. 删除会话/简历不清 Redis 缓存

**问题**：`InterviewSessionCache.deleteSession` **写了但零调用**。`DELETE /api/interview/sessions/{id}` 只删 DB；`ResumeDeleteService` 删简历也只删 DB。已删除的会话在缓存里**最长存活 24h**，`GET /sessions/{id}` 会返回幽灵会话，`interview:resume:{resumeId}` 映射若指向未完成态还会被当成有效未完成会话。

**修复**：
- `InterviewSessionService` 新增 `deleteSession(sessionId)` 与 `deleteSessionsByResumeId(resumeId)`：先删 DB（真相源），成功后清缓存与映射
- `InterviewController` 的删除接口改走 Service
- `ResumeDeleteService` 改依赖 `InterviewSessionService`
- `InterviewSessionCache` 新增公开的 `deleteResumeSessionMapping(resumeId)`——删除简历时会话缓存可能已过期，不能靠会话缓存反查 resumeId

### 🟡 3. 建会话时 DB 写失败被静默吞掉

**问题**：`createSession` 持久化失败只 `log.warn`，而缓存已写入 → 造出「缓存有、数据库无」的会话，缓存过期后进度彻底丢失。这与答题路径「DB 失败必须报错」的可靠性要求相矛盾。

**修复**：捕获后**先 `sessionCache.deleteSession` 回滚缓存，再抛 `INTERVIEW_SESSION_SAVE_FAILED(3009)`**（新增错误码）。

### 🟡 4. 缓存与 DB 状态分叉 + 隐式状态回退

**问题**（三个子问题）：
- 异步消费者**只改 DB 状态、从不改 Redis** → 评估完成后缓存长期停留在 `COMPLETED`，与 DB 的 `EVALUATED` 不一致
- `saveAnswer`（暂存）在 DB 侧**无条件**写 `IN_PROGRESS` → 若在 `EVALUATED` 之后调用，会把 DB 状态打回进行中，缓存 miss 重建后 `GET /report` 以 3007 失败
- `updateCurrentQuestionIndex` 在改索引时**顺带硬编码** `IN_PROGRESS`，职责混乱（同一流程紧接着就显式设了状态）

**修复**：
- 两个消费者（Rabbit / Stream）在评估成功后调 `syncEvaluatedStatusToCache`，把缓存状态同步为 `EVALUATED`；**同步失败只告警**，不影响 ACK 与主流程（缓存是派生态）
- 新增 `InterviewPersistenceService.markInProgressIfUnfinished(sessionId)`，仅当状态是 `CREATED`/`IN_PROGRESS` 时才置为进行中，暂存答案改调它
- `updateCurrentQuestionIndex` 只改索引，不再改状态（状态由 `persistSubmittedAnswer` 显式设置）

### 🟡 5. 文字面试没有任何超时清理

**问题**：全模块零 `@Scheduled`（对比语音面试有 30s 心跳守护、5 分钟暂停超时、2 小时僵尸清理），而 `ErrorCode.INTERVIEW_SESSION_EXPIRED(3002)` **定义了但零引用**。僵尸会话永久累积，并被反复当成"可继续的会话"。

**修复**：新增 `cleanupStaleSessions` 定时任务（见 5.5），阈值 24 小时，每小时执行一次，启动后延迟 10 分钟首次执行。

### 🟡 6. 报告详情页不会自动刷新

**问题**：`App.tsx` 的详情页只在 `sessionId` 变化时请求一次，**没有轮询**。评估未完成时进详情页会看到 `overallScore = null` 渲染成 `-` 并**卡住不动**（轮询只存在于记录列表页）。

**修复**：详情页在 `evaluateStatus` 为 `PENDING`/`PROCESSING` 时用 `setTimeout` 链式轮询（3s），评估出结果自动停止；用 `cancelled` 标志 + `clearTimeout` 做卸载清理，避免请求堆积与内存泄漏。

## 九、面试问答要点

**「缓存和数据库怎么保持一致？」**
> 缓存是**可重建的派生态**：写的时候 DB 优先，DB 成功才更新缓存，缓存失败只记日志；读的时候缓存 miss 就从 `questionsJson` + `interview_answers` 重建并回写。所以 Redis 整体挂掉也不丢进度。状态一致性上我做了两件事：评估完成后消费者会同步缓存状态；暂存答案只在会话未结束时才标记进行中，避免把已评估的会话打回进行中。

**「一个会话有几种状态？」**
> 两条独立的轴：业务状态 `CREATED → IN_PROGRESS → COMPLETED → EVALUATED`，和异步评估状态 `PENDING → PROCESSING → COMPLETED/FAILED`。业务状态里没有 FAILED——评估失败时业务上仍是"已完成"，失败只体现在评估状态上。这个区分让前端能准确展示「已完成 / 评估中 / 评估失败」三种。

**「怎么保证评估不重复执行？」**
> 双保险：消费端先判 `evaluateStatus == COMPLETED` 直接 ACK；落库端用 `evaluation_message_id` 唯一列兜并发，并且 `saveReport` 返回 `CREATED / ALREADY_COMPLETED / SESSION_MISSING` 三态。重试是 10/30/60 秒三档，最终失败进死信并落审计表，管理端可以重放。

**「你觉得这个模块还有什么问题？」**（本次修完剩下的）
> ① `GET /report` 同步评估接口和 `PUT /answers` 暂存接口前端都没用，属于半成品；
> ② 报告详情页现在会轮询了，但评估失败后普通用户仍没有"重新评估"入口，只能走管理员死信重放；
> ③ `SessionStatus` 存在两份枚举定义，靠手工 switch 映射，可以直接统一。
